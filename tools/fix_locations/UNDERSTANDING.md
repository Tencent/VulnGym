# #4 半页理解卡（背这张就够把关）

## 一句话

脚本只做一件事：让标注里的 `code`，在对应漏洞 commit 的源码里，出现在正确的 `file`/`line`。  
**对不上且找不到唯一位置 → 交给人；绝不猜。**

## 三个词

| 词 | 意思 |
|----|------|
| **entry_point** | 外部怎么进来（请求/入口） |
| **critical_operation** | 漏洞真正发作的那一行 |
| **trace** | 中间怎么走到发作点的几步 |

每个节点都长这样：`{file, line, code}`（`desc` 可有可无，我们默认不改）。

## 三级匹配（为何按这个顺序）

标注说「在 A 文件第 N 行是这段 code」，但经常对不上。于是：

1. **邻域 ±5**：只是行号偏了几点 → 最安全  
2. **全文件**：文件对、行号漂了 → 仍较安全  
3. **全仓库**：文件路径也可能错 → 只有**全库唯一命中**才改；多个命中 → 人工  

越往后越容易误伤，所以必须「唯一」才自动改。

## 四种结果（你看 CSV 时用）

| 结果 | 含义 | 你要不要慌 |
|------|------|------------|
| **ok** | 现在就能对上 | 不用改 |
| **fixed** | 唯一找到了，改了 line/file | 抽查是否真对 |
| **needs_human** | 0 个或多个候选，或片段太烂 | **这是合格交付的一部分** |
| （退化片段） | 例如 `code` 只是 `}` | 即使行对得上，也标人工（语义问题） |

## 把关只问三句

1. 这条 fixed：打开源码，那一行是不是这段 `code`？  
2. 这条 needs_human：是不是因为不唯一/找不到/退化片段？（不该被自动改）  
3. 有没有为了「修得多」而猜位置？（有 = 打回）

## 和 #6/#7 的边界

- **#4**：位置修准  
- **#6/#7**：选点是否语义正确（入口是不是真入口）  

行上真是 `}`，位置算对，但语义烂 → #4 记 `needs_human`，不假装完美。
